# Expense Tracker API Reference — Frontend Integration Guide

Base URL: `/api`. The Next.js frontend proxies `/api/*` to this backend, so the browser
always calls its own origin (e.g. `https://expenses.example.com/api/...`).

All request and response bodies are JSON. Interactive docs (development only): `/api/docs`.

**Auth:** session cookie. `POST /auth/login` sets an `HttpOnly`, `SameSite=Lax` cookie
(`et_session`); the browser sends it automatically. There are no bearer tokens and nothing to
store client-side. Every endpoint except `/health` and `/auth/login` requires the cookie.

**Money** is a decimal **string** with two places (`"1250.00"`), never a JSON number, so
nothing is ever parsed as a float. Send amounts as strings too (`"250"` or `"250.50"`).

**Dates** are calendar dates `"YYYY-MM-DD"` with no time or timezone. Timestamps
(`created_at`, `updated_at`) are ISO-8601 with offset.

**Ownership:** every resource belongs to the signed-in user. Asking for someone else's id returns
`404`, exactly like an id that doesn't exist.

**Recurring entries** are materialised on read: any endpoint that returns transaction data first
creates the occurrences that are due, so totals are always current.

**Errors** always have this shape:
```json
{ "error": { "code": "validation_error", "message": "Some fields are invalid.", "fields": { "amount": "Input should be greater than 0" } } }
```
| Status | `code` | When |
|---|---|---|
| 401 | `not_authenticated` | No/expired session → send the user to login |
| 401 | `invalid_credentials` | Wrong email or password on login |
| 404 | `not_found` | Missing, or not yours |
| 422 | `validation_error` | Bad input; `fields` maps field name → message |
| 429 | `too_many_attempts` | 5 failed logins in 15 min for that email |
| 500 | `server_error` | Generic message only; details are in server logs |

## Auth

### `POST /auth/login`
No auth. Body `{ "email": "you@example.com", "password": "••••••••" }`.
`200` → `User` and sets the session cookie. `401`/`429` as above.

### `POST /auth/logout`
Revokes the session and clears the cookie. `204`. Safe to call when signed out.

### `GET /auth/me`
`200` → `User`:
```json
{ "id": "uuid", "email": "you@example.com", "name": "Your Name", "last_payment_method": "upi" }
```
`last_payment_method` (`upi|cash|card|bank|null`) is what the expense form should pre-select;
the server updates it whenever an expense or recurring entry is saved with a method.

## Categories

### `GET /categories?kind=expense|income`
Expense categories and income sources, in display order. Omit `kind` for both.
```json
[{ "id": 1, "kind": "expense", "slug": "food", "name": "Food", "icon": "utensils", "color": "orange" }]
```
Never hard-code ids; use `slug` if you need a specific one (e.g. `salary`). `icon` is a key the
frontend maps to an icon.

## Transactions

`Transaction`:
```json
{
  "id": "uuid", "type": "expense", "amount": "250.00",
  "category": { "id": 1, "kind": "expense", "slug": "food", "name": "Food", "icon": "utensils", "color": "orange" },
  "description": "Lunch", "occurred_on": "2026-09-24",
  "payment_method": "upi", "recurring_rule_id": null,
  "created_at": "2026-09-24T13:20:00+05:30", "updated_at": "2026-09-24T13:20:00+05:30"
}
```
`payment_method` is only allowed on expenses. `recurring_rule_id` is set when the entry was
generated by a recurring rule (show the repeat icon).

### `POST /transactions`
```json
{ "type": "expense", "amount": "250", "category_id": 1, "description": "Lunch", "occurred_on": "2026-09-24", "payment_method": "upi" }
```
`description` optional (≤ 200 chars). The category must match `type`. `201` → `Transaction`.

### `GET /transactions/{id}` · `PATCH /transactions/{id}` · `DELETE /transactions/{id}`
`PATCH` is partial; send only what changed. Changing `type` also requires a matching
`category_id`; switching to income clears `payment_method`. `DELETE` → `204`.

### `GET /transactions?type=&year=&month=&cursor=&limit=`
Newest first, cursor pagination (`limit` 1–100, default 30). `year`+`month` go together.
```json
{ "items": [ /* Transaction */ ], "next_cursor": "opaque-string-or-null" }
```

## Home

### `GET /dashboard/monthly?year=2026&month=9&today=2026-09-24`
Everything the home screen needs in one call. `today` is the device's date (defaults to today in
`APP_TIMEZONE`).
```json
{
  "year": 2026, "month": 9,
  "total_income": "50000.00", "total_expenses": "18450.00",
  "income_count": 1, "expense_count": 25,
  "today": { "date": "2026-09-24", "total_expenses": "510.00", "expense_count": 3, "total_income": "0.00" },
  "comparison": { "year": 2026, "month": 8, "through_day": 24, "total_expenses": "15500.00", "total_income": "50000.00" },
  "expense_breakdown": [{ "category": { }, "amount": "4250.00", "count": 9, "previous_amount": "3100.00" }],
  "recent_transactions": [ /* 6 × Transaction */ ]
}
```
- `today` is always about `today`, whichever month is requested.
- `comparison` is the previous month **up to the same day** when the requested month contains
  `today` (`through_day` set → "vs 1–24 Aug"), otherwise the whole previous month
  (`through_day: null` → "vs August"). Each category's `previous_amount` uses the same window.
- There is deliberately no balance anywhere.

## History

### `GET /history/monthly?year=2026&month=9&type=expense|income`
A month of transactions grouped by day, newest first.
```json
{
  "year": 2026, "month": 9, "entry_count": 26,
  "total_expenses": "18450.00", "total_income": "50000.00",
  "days": [{ "date": "2026-09-23", "total_expenses": "450.00", "transactions": [ /* Transaction */ ] }]
}
```
`type` filters `days[].transactions`; `entry_count` and the totals always cover the whole month,
and `days[].total_expenses` is the day's full expense total.

## Insights

### `GET /insights/monthly?year=2026&month=9&today=2026-09-24`
```json
{
  "year": 2026, "month": 9, "total_expenses": "18450.00",
  "daily": [{ "date": "2026-09-01", "amount": "1000.00" } /* every day of the month */],
  "days_elapsed": 24, "average_daily": "769", "no_spend_days": 3,
  "highest_day": { "date": "2026-09-05", "amount": "1850.00" },
  "payment_methods": [{ "method": "upi", "amount": "9000.00", "count": 14 }],
  "trend": [{ "year": 2026, "month": 4, "total_expenses": "17200.00", "total_income": "50000.00" } /* 6 months, oldest first */],
  "trend_average_expenses": "16980"
}
```
Averages are rounded to whole rupees. `payment_methods` lists only methods with spending
(`method: null` = older entries without one).

## Recurring

`RecurringRule`:
```json
{
  "id": "uuid", "type": "expense", "amount": "999.00", "category": { },
  "description": "Internet", "payment_method": "upi",
  "day_of_month": 3, "start_on": "2026-09-03",
  "next_run_on": "2026-10-03", "last_run_on": "2026-09-03", "is_active": true,
  "created_at": "…", "updated_at": "…"
}
```

### `GET /recurring`
All rules, active first.

### `POST /recurring`
```json
{ "type": "expense", "amount": "999", "category_id": 4, "description": "Internet", "payment_method": "upi", "start_on": "2026-09-03" }
```
`start_on` is the first occurrence; its day of month repeats every month (clamped in short
months). Occurrences due up to today are created immediately. `201` → `RecurringRule`.

### `GET /recurring/{id}` · `PATCH /recurring/{id}` · `DELETE /recurring/{id}`
`PATCH` fields: `type`, `amount`, `category_id`, `description`, `payment_method`,
`day_of_month` (1–31), `is_active` (pause/resume; resuming doesn't backfill missed months).
Changes apply to future occurrences only. `DELETE` → `204`; entries already created stay.
